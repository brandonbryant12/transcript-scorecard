How a call becomes a score, evidence and coaching

This page explains how the system scores a support call while it is happening, how it finds the turns that justify each score, how it reads the customer's emotions, what it tells a coach, and how coaches check whether any of it can be trusted. It gives the reasoning behind each decision so you can change the system without first reverse-engineering it.

1The system in one picture

A call arrives as a sequence of turns: one speaker, one stretch of speech. The system keeps a scorecard that says what good looks like. Every time a few new turns arrive it writes a set of narrow, typed questions, sends them with the transcript to a decision model, and receives a probability for each. Those probabilities are stored as readings. A pure function then composes the readings into an evaluation: a score per skill, an overall score, the turns that serve as evidence, the customer's emotional journey, and coaching points.

Separately, a coach can rate the same call on the same scorecard without seeing the AI's answer. Comparing the two tells you how far to trust the evaluation, and which thresholds to move.

Five terms carry the rest of the page:

Skill
A weighted line on the scorecard, such as "Resolution & ownership", with an ordered rubric of described levels.
Behaviour
One observable action that is either true of a single employee turn or not, such as "The employee restates the customer's problem".
Reading
One probability returned by the model, stored against the turn, skill or behaviour it was asked about.
Pass
One round of questions against the call so far. A live call gets many passes; a finished transcript gets one.
Observability
The probability that the call gives a fair basis to judge a skill. It decides how much that skill counts.

2What was wrong before

The first version asked one rubric question per criterion and one "which turn is the best evidence?" question per criterion, and repeated all of them on the whole transcript every five turns. It produced plausible numbers. It also had six problems, and each one shaped the redesign.

Vague rubricLevels were bare labels such as "Adequate" and "Strong". One criterion, "Accuracy & policy alignment", bundled accuracy, identity checks and unsupported promises.Every level has a description, and bundled criteria are split into separate skills.

It could not show a strength and a failure in the same skill, and it put the whole transcript into the options of every evidence question.A yes/no question per behaviour per employee turn. 3What a decision model allows

The Gemini Decisions API, OpenAI Decisions and TypeSafe JEV share one shape. You send an input and a set of questions. Each question is one of three types, each is answered independently against the same input, and each answer is a calibrated probability. The model writes no text at all, which is why a request with hundreds of questions returns in a few hundred milliseconds and costs input tokens only.

Question typeReturnsUsed here for
Yes / noProbability of yes"Did this behaviour happen in this turn?", "Can this skill be judged yet?", "Was this behaviour called for?"
ChoiceOne option and a probability for every optionThe customer's emotion in one turn
Ordered rubricA probability per level and their weighted averageSkill ratings, customer sentiment, escalation risk

Three consequences follow, and the whole design leans on them.

  • Questions are atomic and the logic lives in code. Questions cannot see each other, so there is no point writing one clever question that tries to weigh several things. Ask many narrow ones and combine the answers with ordinary arithmetic and if statements. That also makes every combination rule readable and testable.
  • The model cannot write coaching. It returns numbers. Every sentence a coach reads therefore has to exist already, written by a person in the scorecard: behaviour names, tips and level descriptions. The code decides which of those sentences a call has earned.
  • Confidence is usable. Because answers are probabilities rather than prose, the system can tell hesitating from knowing, and route the uncertain cases to a person.

The three providers differ only in wire format. An adapter per provider translates to one neutral contract, and all answers pass through one validator that rejects a missing answer, a wrong type, a probability outside 0 to 1, a choice that was not offered or a rubric score outside its range. A bad answer fails the pass. It is never replaced with a default, and a provider's error body never reaches the browser because it can echo the transcript or a key.

// The neutral contract every provider adapter translates to and from
type Question =
  | { type: "noul";   instructions: string }                                   // yes / no
  | { type: "choice"; instructions: string; options: Record<string, string> }
  | { type: "score";  instructions: string; levels: string[] }                 // ordered, index 0 is lowest

type Answer =
  | { type: "noul";   probability: number; confidence: number }
  | { type: "choice"; choice: string; confidence: number; probabilities: Record<string, number> }
  | { type: "score";  score: number; confidence: number; probabilities: number[] }

4Skills and behaviours

A scorecard is a list of weighted skills. Each skill is judged in two ways at once, because the two ways are good at different things.

The rubric gives the number

Each skill has an ordered rubric of two to ten levels, and every level has a label and a description. The description matters more than the label: the model picks "the level whose description fits best", and adjacent levels have to be clearly different for that to work. This is the Resolution rubric in the default scorecard.

LevelLabelDescription
0UnresolvedNo fix and no plan; the customer is left where they started.
1Weak next stepA vague or unowned follow-up with no timeframe.
2PartialSome progress, but part of the issue is still open or unowned.
3ResolvedThe issue is fixed, or has a specific next step with an owner and a timeframe.
4Resolved and proactiveFixed and confirmed with the customer, with future problems anticipated and prevented.

The scale is linear on purpose. The returned score is the probability-weighted average of the level indices, so levels that are not evenly spaced would skew it.

Behaviours give the evidence and the coaching

A behaviour is a statement that is true or false of one employee turn. It has a polarity, an optional situation in which it is expected, a flag for critical failures, and a tip written by whoever owns the scorecard.

FieldMeaningExample from the default scorecard
statementWhat is checked against a single turn"The employee restates or summarises the customer's problem in their own words to confirm understanding."
polaritypositive: should happen. negative: should not."Makes an unsupported promise" is negative.
expectedWhenThe situation that calls for a positive behaviour. Empty means every call."The customer has described the problem they need help with."
criticalA negative behaviour that raises a flag on the whole call"Unverified account change"
tipThe advice shown when the behaviour is missed or violated"Play the problem back and ask whether you have it right before you start troubleshooting."

Behaviours answer the question a rubric cannot: where. "Accuracy: 35" is a verdict. "Made an unsupported promise at turns 22 and 24" is something a coach can play back.

Why both, and why the rubric owns the number

Counting behaviours would give a score, but a poor one. A checklist rewards saying the right words and cannot weigh a recovery against a slip. The rubric makes a holistic judgement and is directly comparable with a coach's rating on the same levels. So the rubric produces the skill score, and behaviours explain it. The two are asked independently, which gives a free consistency check: when they contradict each other the evaluation is sent to a person (section 9).

Weights do not need to total 100. The overall score divides by the weight that actually counted, so the two media skills simply drop out of a transcript-only call (section 11).

Versions are immutable

Publishing an edit never changes a scorecard in place. It creates the next version, and every run, evaluation and coach review records the version it was made against. Without that, changing one level description would silently change the meaning of every stored score, and a coach's rating could be compared with an AI rating made on a different rubric. Publishing an unchanged definition creates nothing.

5Two lanes of questions

Each pass sends one shared input, the transcript so far, and questions from two lanes. The split exists because some facts about a call are settled the moment a turn is spoken and others keep changing until the call ends.

Turn lane: read each turn once

Whether the employee restated the problem in turn 8 does not change when turn 30 arrives. So for every employee turn that has not been read yet, the plan asks one yes/no question per behaviour, and for every new customer turn it asks for sentiment and emotion. The answers are stored against the turn and never asked again. The cost of this lane grows with the length of the call, not with its square.

Focus on the single turn labelled [turn-18]; treat every other turn as context only.
Is this statement true of that turn? Statement: The employee makes, or offers to make,
a change to account access, credentials or contact details without verifying the
identity of the person affected.

Call lane: asked again on every pass

A skill rating, by contrast, is a judgement about the whole call so far and has to be refreshed. On every pass the call lane asks:

  • One rubric rating per skill. "Rate the EMPLOYEE on "Resolution & ownership": … Judge only what the transcript shows so far; do not guess how the call will end. Choose the level whose description fits best."
  • One gate per skill. While the call is live: "Has it progressed far enough to fairly judge the EMPLOYEE on …? Answer yes only if the employee has already had a real opportunity to show this skill." Once the call is over the wording becomes "Did this call give the EMPLOYEE a real opportunity to show …? Answer no only if nothing in the call called for this skill."
  • One "was it called for?" check per conditional behaviour. "Has this situation come up at any point in the call so far? Situation: The customer has asked for a guarantee, a timeframe, or certainty about an outcome."
  • Escalation risk. "If the call ended right now, how likely is the CUSTOMER to escalate, complain, or stop using the company?"

How many questions

With S transcript skills, B behaviours on them and E conditional positive behaviours, a pass asks 2S + E + 1 call-lane questions plus B per new employee turn and 2 per new customer turn. For the default scorecard that is 5 + 5 + 12 + 1 = 23 call-lane questions and 16 per employee turn. A request above 300 questions is split into parallel requests against the same input; if any one of them fails, the whole pass fails and the readings stay as they were, because a half-read call would look complete.

How the transcript is presented

The shared input is plain text with one line per turn and a bracketed label, so a question can point at exactly one turn:

Customer support call about: Cannot connect smart hub
EMPLOYEE is Avery Morgan, the support employee being assessed. CUSTOMER is Robert Davis.
The call is still in progress. This is the transcript so far.

[turn-17] CUSTOMER: I need to leave soon. Can my partner call if it does not finish?
[turn-18] EMPLOYEE: Yes, I can add them now. Just give me their full name and email address.

Each turn's text is flattened to a single line first. Transcript content is untrusted, and without that step a turn containing a line break and a fake [turn-99] label could pose as another turn.

The model never sees question keys. Keys are short and opaque (t_17_9), and a table kept beside the request records what each one means, so user-defined skill and behaviour ids never have to satisfy a provider's key rules.

7From answers to a score

Composition is one pure function, composeEvaluation(definition, state, turns, stage). It takes the stored readings and returns the evaluation, with no network and no randomness. Because it is pure, a threshold can be changed and every stored call re-composed without paying for a single new request. The constants it uses live in one object and are stamped on every evaluation through the method version.

ConstantValueMeaning
detectThreshold0.60A behaviour counts as detected in a turn at or above this probability.
expectedThreshold0.50A positive behaviour counts as called for at or above this probability.
minCoverage0.10Below this share of judgeable scorecard weight there is no overall score yet.
observableThreshold0.50A skill is treated as judgeable for coaching at or above this.
reviewAdjacentMass0.75Below this, the model is torn between distant levels and a person should look.
shiftThreshold0.40Smallest change in valence between customer turns that counts as a shift.

Behaviour status

A behaviour's status comes from two readings: the strongest tag across employee turns, and (for conditional positive behaviours) the probability that it was called for.

PolarityConditionStatus
PositiveDetected in at least one turndemonstrated

"Missed" needs the second reading. Without it, a call in which nobody asked for a guarantee would mark "Sets honest expectations" as a failure. A behaviour with no expectedWhen is expected on every call, and can only be called missed once the call is over; while the call is live it stays "not applicable", which the interface can show as "not yet".

Skill score

The model returns a probability for each rubric level. The skill's expected level is the weighted average of the level indices, and the normalised score is that level divided by the top index, times 100. The evaluation keeps the whole distribution, the most likely single level and the model's confidence in it, because two very different distributions can share one average.

Overall score: weight by how fairly each skill can be judged

The gate reading for each skill is its observability. Each skill counts in proportion to its weight times its observability:

overall  = Σ (weight × observability × score) ÷ Σ (weight × observability)
coverage = Σ (weight × observability) ÷ Σ weight

Coverage is the share of the scorecard the call has given a fair basis to judge. A live score always travels with it, so "74 on 48% of the scorecard" is read differently from "74 on 93%". If coverage is under 10% there is no overall score at all.

Why the weighting is soft, and why it applies after the call too

Observability is used as a continuous weight, with no cut-off. A cut-off would make the live score jump the moment a gate crossed it, and would discard the information that a skill is, say, 60% judgeable.

The gate is asked on the final pass as well, with different wording. Early in the design it was forced to 1 at the end, on the theory that a finished call can be judged on everything. That is false. A two-minute trial cancellation gives an employee almost no chance to show empathy; on the seeded call call-1005 the gate for Empathy came back at 0.32. Forcing it to 1 would have counted a generic "Adequate" at full weight. A coach would mark that skill "not applicable", and the system now does the proportional equivalent.

8The customer's side: sentiment, emotion and risk

These signals describe the customer. They never enter the employee's score. A customer can be furious for reasons the employee did not cause, and an employee can do everything right and still deliver bad news. What the signals are for is context: they show a coach which moments mattered.

Two readings per customer turn

  • Sentiment is an ordered rubric with five described levels, from "Very negative: angry, hostile, or threatening to leave or escalate" to "Very positive: delighted or openly grateful". The expected level (0 to 4) is rescaled to a valence between −1 and +1 with (level − 2) ÷ 2. An ordered scale gives a number that can be plotted and differenced.
  • Emotion is a choice among six labels, each with a description: anxious, cooperative, frustrated, neutral, reassured, skeptical. A label says what kind of negative: anxious and frustrated call for different responses.

Two details of the emotion question come from how choice questions behave. A choice always spreads its probability across the options given, even when none fits, so "neutral" is an explicit option with its own description. And the Gemini API sorts option keys alphabetically before evaluating them, so no key depends on its position; a catch-all called "none_of_the_above" would sort into the middle of the list.

Reading every customer turn separately replaced a single label for the call. The longest seeded call ends with a satisfied customer, and a single label would have said only that. The per-turn readings show a customer who started at a valence of about −0.5, hit bottom at turn 6 after being told to restart the router a third time, and recovered once the employee apologised and restated the problem.

Shifts and the arc

A shift is a change in valence of at least 0.4 between two consecutive customer turns. Each shift records the employee turns that sit between them, which is what links emotion to behaviour: if a detected behaviour falls in those turns, its coaching point is marked with the direction the customer moved. A positive behaviour before an upward shift is a strength that visibly worked. A negative behaviour before a downward shift is the first thing to coach.

The arc is one label for the whole journey, classified from the average of the first two readings, the average of the last two, and the lowest point.

ArcRule, checked in this order
recoveredThe low point is at or below −0.35 and the end is at or above +0.2
improvedEnd minus start is at least +0.35
declinedEnd minus start is at most −0.35
steady positive / neutral / negativeOtherwise, by whether the average valence is above +0.2, below −0.2 or between

"Recovered" is checked first because it is the story a coach most wants to find: the customer was lost and the employee won them back.

Escalation risk

One rubric question on every pass asks how likely the customer is to escalate, complain or leave if the call ended now, on four levels from "Low" to "High". It is a call-level reading and is replaced on each pass, so in a live session it behaves like a gauge.

9Coaching without generated text

The model cannot write, so coaching is assembled. buildCoaching walks the composed skills and picks sentences that already exist in the scorecard.

OutputBuilt fromText shown
Strengths (up to 3)Demonstrated behaviours, ranked by skill weight times detection probability. One that preceded an upward sentiment shift goes to the top.The behaviour's name and statement, with its turns
Opportunities (up to 3)Violated behaviours first, then missed ones ranked by skill weight times how clearly they were called for.The behaviour's name and its tip

The focus is chosen by points lost, weighted, and by nothing else. The lowest-scoring skill is often a low-weight one that would move the overall score least. And the target is the next level's description because "get to Exceptional" is no use to someone sitting at "Partial"; the rubric already contains the sentence that describes one step up.

When an evaluation asks for a human

An evaluation is marked as needing review for any of three reasons.

  • A critical behaviour was detected. A possible security breach is always worth a person's time.
  • The model is torn between distant levels. The adjacent mass of a skill is the probability on its most likely level plus the levels immediately either side. Below 0.75 the model is putting real weight on levels two or more steps apart, which means it does not know whether the performance was good or bad.
  • The rubric and the behaviours contradict each other. A skill rated at the top level although a problem behaviour was detected in more than one turn, or rated in the bottom two levels although every expected behaviour was detected and none was violated. They were asked independently, so one of them is wrong. A single slip does not trigger this, because the top rubric level for Empathy explicitly includes repairing a misstep.

Why low confidence alone is not the trigger

The first version flagged any skill whose confidence, the probability of its most likely level, was under 0.5. On the first four calls scored it flagged all four. The cause was ordinary: with five levels, a model that is split 0.47 to 0.45 between "Accurate" and "Precise" has a confidence of 0.47 and no real doubt about the employee. Hesitating between neighbours is how a well-calibrated model should rate a performance that sits between two descriptions.

10Scoring during the call

A live session is a call whose turns are still arriving. The scoring pass is the same function used for a finished transcript; only two things differ. The stage is provisional until the input ends and final on the last pass, which changes the wording of a few questions. And the readings from earlier passes are handed back in, so turns already read are skipped.

One pass in flight, and turns coalesce

A pass is owed when the number of unscored turns reaches the session's "score every N turns" setting, and always once the input is complete. At most one pass per session runs at a time. Turns that arrive while a pass is running simply wait, and the next pass picks all of them up together. So a slow provider makes passes larger and less frequent. It never builds a queue of stale requests, and the session never falls further behind than one pass.

Each pass writes a full evaluation. The interface subscribes to the session over Server-Sent Events (GET /api/live/:id/events) and is pushed the whole session after every change: a new turn, a pass starting, a pass finishing. Each push carries the latest evaluation, the score history and the request ledger. A reset gives a replay a fresh run, so the abandoned run's evaluations and requests stay attributable, and a result that returns after a reset is dropped because its run id no longer matches.

Sources

  • Replay reveals a stored transcript one turn per interval. It is how the seeded demo calls are played.
  • Stream is an ingest API. POST /api/live/stream opens a call, POST /api/live/:id/turns appends a turn with a speaker and text, and a control action of end says the call is over. Anything that produces turns can use it: a contact-centre transcription feed, a meeting bot, a test script.
  • Voice practice call uses a real-time voice model, Gemini Live (gemini-3.8-live), to play the customer while a person speaks as the employee. The Live API transcribes both directions as it goes: input transcription is the employee, output transcription is the customer. That gives speaker-attributed turns with no separate speech-to-text step, and they enter scoring through the same path as a stream. The model sits behind an interface, so another real-time model can replace it.

How a voice call becomes turns

A practice call is one WebSocket from the browser. Microphone audio goes up as 16 kHz PCM, with an optional camera frame once a second; the customer's voice comes back as 24 kHz PCM. The server holds the voice model's connection and its API key, so the browser never talks to the model directly. Three details turn that continuous exchange into scoreable turns:

  • Turn boundaries come from the voice model. The model starting to reply means the employee has finished. The employee's turn is closed 600 ms later, because their transcription can trail the first syllables of the reply, and it is always appended before the customer's turn that answers it.
  • Each turn's audio is cut from the stream by time. The Live API reports when the speaker started and stopped as offsets into the audio sent so far. The server keeps a rolling 45-second window of microphone audio and slices the turn out by those offsets, with 0.3 seconds of padding and a 30-second cap. The customer's clip is simply the audio the model generated for that turn.
  • Media rides with the turn. The clip, and up to three camera frames spread across the turn, are attached when the turn is appended, so the pass that reads the turn's words reads its sound and picture too. Clips live in memory for the length of the session and are never written to disk.

The design question in the practice call is what a scoring system looks like when audio is piped through a real-time model. The answer here is that the real-time model's job is the conversation and the transcript, and the decision model's job is judgement. They are separate requests with separate latency budgets, and the scoring side does not care which model produced the turns.

11Transcript, audio and video

If you have the audio, do you still need the transcript? If you have video, do you need either? The answer the design settled on, and which a set of experiments against the live Gemini Decisions API then tested: the transcript is always kept, and audio and video are added to it for what words cannot carry. The experiments, their raw results and a longer set of notes are in docs/research/modalities/NOTES.md; the numbers in this section come from there.

Why the transcript stays

  • It is the cheapest carrier of what was said. Audio was billed at 30 tokens per second in every run (the documentation says 25), so a 10-minute call is about 18,000 tokens of audio. The same call is roughly 3,000 tokens of transcript. On a 67-second test call, the recording answered turn-level questions exactly as well as the transcript (26 of 29 correct for both) at 6 times the tokens and 2.6 times the latency.
  • It is the addressing scheme. A question can say "the turn labelled [turn-18]" and a coach can read and quote that turn. A recording has no labels to point at. Asking about "the fourth time the employee speaks" got 15 of 29 right with 11 false positives; asking by time range worked, but the time ranges come from a transcript or diarisation in the first place.
  • Repeated input is billed in full, and it is slow. The Decisions API has no context caching. Resending the growing recording on every pass over a 10-minute call would cost around 360,000 audio tokens, against 18,000 for reading each second once. Latency is the stronger argument: a request took about 0.4 seconds plus 10 ms per second of audio, so a pass over nine minutes of recording took about six seconds.
  • It comes free with a real-time model. The Live API produces the transcript alongside the audio.

What the other channels add

Audio carries how something was said: pace, warmth, irritation, a sigh. Video carries what was visible: whether the employee was facing the camera or reading another screen. Both signals are real, and measurably so:

ChannelTestResult
AudioActors saying the same neutral sentence in different deliveriesSentiment 0.89 (on the 0 to 4 scale) for the angry delivery against 1.95 for the neutral one; "sounds irritated" at 0.72 against 0.25
VideoSingle frames of one agent in different statesPresence rated 0.7 to 1.0 when slumped or on a phone against 2.5 to 3.6 when attentive or engaged; "looks away" at 0.78 to 0.86 against 0.13 to 0.14

Neither replaces the other, and neither replaces the transcript. A real video clip does carry its own sound (a spoken sentence was recognised from a video block), so one short video clip per turn could stand in for separate frames and audio; that is a planned next step, because it needs the browser to record per-turn clips. Today the practice call captures video as still frames, and frames have no sound. Two cautions from the same experiments: audio adds little when the voice is synthetic, because a text-to-speech voice mostly repeats what its words already say, and the model never answers "there is nothing here". Three seconds of silence came back as an ordinary "neutral" rating.

So every skill declares the channel it is judged from.

How a clip is sent

Media questions travel in their own lane. Each turn's clip gets a request of its own, so a question never has to say which of several recordings it means. A clip is read once and never sent again. Three decisions in this lane were changed by measurement.

The attached audio clip is one turn of a customer support call, spoken by the CUSTOMER.

  + one audio block (the clip of that turn)

Question: Listen to the attached audio clip of the CUSTOMER. Judging by the sound of
their voice (tone, pace and emphasis) rather than the words, how does the customer feel?
  • No transcript travels with a clip. The first version sent the last four turns as text beside the audio, for context. That text pulled the reading towards the words: an angry voice saying something neutral fell from 0.79 to 0.31 on "sounds irritated" once its words sat next to it. A clip now carries one line saying whose voice or picture it is. The words are still read, by the transcript lane.
  • One turn per request. Several labelled clips in one request can be addressed separately, but a neighbouring clip moved one answer by a full sentiment level.
  • A visual behaviour is asked of each frame, and combined in code. Asked over a set of frames, a brief lapse is averaged away: looking away in two frames of six scored 0.33, under the detection threshold. Asked frame by frame, those two frames scored 0.87 and 0.89. So each frame is labelled, each behaviour is asked of each frame, and the turn's reading is the highest frame for a problem behaviour and the average for a good habit. The rubric is asked once over the set, where an overall impression is what is wanted.

There are three kinds of clip request:

  • An employee turn with audio is asked the rubric and the behaviours of every vocal skill, with the instruction to "judge only how the employee sounds in this clip, not the words they chose".
  • An employee turn with video frames (up to three, spread across the turn) is asked the rubric of every visual skill over the frames, and its behaviours frame by frame.
  • A customer turn with audio is asked one question: sentiment from the sound of the voice, on the same five levels used for sentiment from words.

A clip is only sent if there is something in it. Audio shorter than a second, or too quiet to contain speech, is dropped in code before any question is asked, because the model would rate the silence. The transcript questions are unaffected: they go out as before, against the transcript alone, in the same pass.

How media skills are scored

A transcript skill gets one rubric rating for the call so far. A vocal or visual skill cannot work that way without resending the recording, and it does not need to. Tone is a property of each utterance. So a media skill's rubric is asked once per employee turn, on that turn's clip, and the turn ratings are averaged: the expected level is the mean of the turns' expected levels and the level distribution is the mean of their distributions. Its behaviours are tagged from the same clip. Like transcript turns, each clip is read once.

One scorecard for three kinds of call

A call with no audio leaves "Vocal delivery" unassessed. Its observability is 0, its behaviours read "not assessed", and the observability weighting from section 7 removes it from the overall score with no special case. The same scorecard therefore scores a chat transcript, a phone call and a video call, and the scores stay comparable on the skills they share. The evaluation records which channels contributed.

Words and voice can disagree

When a customer turn has audio, sentiment is read twice: once from the words and once from the voice, each without sight of the other. The journey uses their average, weighted equally, and keeps both readings. A turn where the two are a full level or more apart is marked as a mixed signal. Equal weighting is a starting point and should not be tuned without coach labels. Keeping both matters more than the weighting: a customer who says "fine, whatever works" in a flat, clipped voice has high sentiment in words and low in voice, and that gap is exactly what a coach wants pointed out.

Provider support. Only a provider with media input can read the vocal and visual channels, which today means Gemini. On OpenAI Decisions and JEV, media questions are not sent and the media skills stay unassessed. Nothing is approximated from the transcript in their place.

12Ground truth from coaches

Nothing above establishes that the scores are right. Two providers gave the same turn 0.59 and 0.98. The thresholds in section 7 are defaults chosen by looking at a handful of calls. The only way to know whether a score deserves trust, and the only principled way to set a threshold, is to compare the system with people who know what good looks like on calls they have rated themselves.

The review

A coach opens a call and rates it on the active scorecard: a level for each skill, a three-way label for each behaviour, and notes.

  • It is blind. The coach rates before seeing the AI's evaluation, and the comparison appears only after they submit. A coach who sees "AI: Strong" first will anchor on it, and the agreement number would then measure the AI's influence on the coach.
  • It uses the same rubric. The coach picks from the same described levels the model chose between, so the two ratings are directly comparable with no mapping in between.
  • "Not applicable" is a first-class answer. A coach who cannot fairly judge a skill leaves it unrated, and that skill is left out of the comparison. Behaviour labels are yes (it happened), no (it was called for and did not happen, or for a negative behaviour, it did not happen) and n/a.
  • One review per coach per call, pinned to a scorecard version. Saving again replaces that coach's earlier ratings. A draft is work in progress; only submitted reviews count as ground truth.

A rating is compared with an AI rating only when both were made on a rubric with the same number of levels for that skill. A rating made against an older, differently shaped rubric is left out. It is never stretched to fit.

What to review next

Coach time is the scarce resource, so the review queue orders calls by how much a review would teach: calls nobody has reviewed first, then calls the AI marked as needing review, then lowest AI confidence. The queue shows that the AI is unsure. It does not show the score or its direction, so the ordering does not break blindness.

Reading the agreement report

For each provider, the report pairs every submitted review with that provider's most recent final evaluation of the same call and compares them skill by skill.

The human baseline

When two coaches have rated the same call, the report computes the same statistics between them. That number is the ceiling. If two experienced coaches agree exactly 65% of the time, an AI at 62% is performing like a coach, and an AI at 90% would be suspicious. Without the baseline an agreement figure has nothing to be compared with.

Agreement per run

Every scoring run also reports its agreement with the coach reviews of the calls it scored, computed from the flat result rows. That turns a scorecard edit or a provider switch into an experiment: score the reviewed calls again and see whether agreement went up.

13Data model

The database is SQLite with thirteen tables in four groups. Each table is a TypeORM entity kept beside the module that owns it, and the schema is created by migrations rather than synchronised from the entities, so it changes only when a migration says so. Three ideas shape it.

  • Scorecards are versioned and immutable. Runs, live sessions, evaluations and coach reviews each record the version they were made against.
  • Everything the model produced is an evaluation. A batch run writes one final evaluation per call. A live session is a scoring run whose evaluations are provisional until the last. There is no separate "snapshot" concept, and a live session's score history is a query over its run's evaluations.
  • Measurement is first-class. provider_requests is a ledger with one row per API call, successful or not, holding latency, tokens, question count and estimated cost. skill_results and behavior_results repeat an evaluation's key numbers as flat rows, so agreement and trends are plain SQL with no JSON parsing.

15Limits and open questions

What was run against the live Gemini APIs. All of it, on 11 November 2026, the day the Decisions API launched. Gemini Decisions scored the seeded transcripts in batch and in live replays through the adapter written from its documentation, with no changes needed. The Gemini Live practice call ran end to end, with synthesised employee speech standing in for a microphone: Gemini Live answered as the customer, both sides were transcribed into turns, and the per-turn audio clips and camera frames were read by Gemini Decisions. In the run with frames, "Looks away" was detected on exactly the one turn that was sent a frame of someone looking at another screen, and "Faces the camera" on the other two. One thing the documentation gets wrong: the Live WebSocket quickstart puts responseModalities at the top level of the setup message, which the API rejects; it belongs under generationConfig.

  • How well a decision model reads tone and expression on real calls is not established. The modality experiments used sixteen acted voice clips from two actors, four acted videos, six generated frames and one synthetic call. They show the signals exist and shaped how clips are sent. They say nothing yet about subtle, noisy, overlapping real speech, and the vocal and visual thresholds are provisional until coaches label real recordings.
  • Thresholds are defaults. 0.6 for detection, 0.5 for "called for", 0.75 for adjacent mass and 0.4 for a sentiment shift were chosen by inspecting a few calls. The worked example already shows one provider landing at 0.59. They should be set per provider from coach labels.
  • Fusing words and voice at 50/50 is a default, not a finding.
  • The demo data is small and fictional. Nine scripted calls were written to contain clear behaviours. Real calls have crosstalk, transcription errors and ambiguity. Agreement on these calls would say little about production.
  • The transcript is untrusted input. A customer or employee can say things that argue for a classification. Narrow questions, described levels and line flattening reduce the risk. They do not remove it, and a critical flag should lead to a human check, never to an automatic action.
  • Blind review is a workflow guarantee. The interface hides the AI's evaluation until a review is submitted. The API has no authentication and would return it to anyone who asked.
  • Long calls resend the transcript. The turn lane reads each turn once, but every pass sends the whole transcript so far as shared input. For a call of an hour or more the next step is to give turn-lane questions a window of recent turns and keep the full transcript for the call lane.
  • A turn is tagged with what was known when it was read. In a live call a turn is judged against the transcript up to that pass. A behaviour that only becomes clear in hindsight, such as a statement the customer contradicts later, can be missed live and caught in a batch re-score.
  • Coaching can only say what the scorecard says. That is a deliberate constraint and also a real limit: advice is only as specific as the tips its author wrote.
  • The customer in a practice call is synthetic, and so far the employee was too. A voice model's emotional range is not a real customer's, and the practice calls measured here used text-to-speech for the employee and generated images for the camera. They show the pipeline works. They do not show how well tone and expression are read on real people.
